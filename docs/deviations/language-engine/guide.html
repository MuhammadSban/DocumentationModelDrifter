Drifter beyond Python

Drifter reads only Python today. The proposal adds one tree-sitter engine, written once. After that, each new language is a row of settings and a query file of about five lines, not new code. The model files stay exactly as they are.

A proposal on branch phase5-kk, not built. Nothing here changes the contract or the spec until the team accepts it.

The plan: Python moves in four steps

      
The 14 languages come first, while Python stays on CPython ast. Then Python moves onto the same engine one model at a time, and only after its output is proven byte-identical. Pick a step to see what it builds and the gate it must pass. Red boxes are TEMPORARY, the same marking the md diagrams use.

      
Sources: 04, Steps a to d, README, Where Python is hard-wired, 01, The picture

When the grammar cannot read a file

      
tree-sitter reads code as written, so macros, syntax newer than the grammar, and deliberately broken test files leave ERROR regions. Four fixes run before parsing. What is left is handled per language: a fail row stops the check with PARSE_FAILED, and a skip row reads the rest of the file and lists it as partly read.

      
Sources: 04, Parse errors, research-template-engine, section 3

Four fixes, applied before parsing

        
Each replaces whole lines with spaces of the same length, so every other byte keeps its position.

        

      

    

  







  

    

      
The engine: fast enough, and lighter than today

      
Measured on 15 real repositories: 32,393 files and 4.15 million lines, on one core. Parsing runs in C and takes 65 % of the time. The big savings come from parsing each file once, dropping each tree as soon as its facts are out, and caching facts by git blob id.

      
Sources: research-template-engine, section 2, 04, How the engine runs efficiently

Today, and the end state after step d

      
After step d, one module, extract, turns in-scope file text into facts. Every language, Python included, is a row plus a query file behind it. The two models become small views of the same facts.

What the interface promises

        

          
            
InputRepo-relative path to decoded text. Size and encoding are already judged by check.py

            
OutputSame files in, same bytes out: no clock, no hash seed, no thread order

            
ErrorParseFailed(path, line, reason) for the first failing file in path order, only from a fail row. Code PARSE_FAILED

            
Unknown extensionNot an error. No row claims it, so it gives no facts

            
NeverImports, runs or builds the analysed code (REQ-06). Never reaches the network

    C and C++: keep, ship last
    
          
    After M1 to M4 a failing file is still about 97 % readable, and the #include graph almost never falls inside an error region. They need skip (O2), all four fixes and validation on more repositories. Running the real preprocessor is rejected: its output depends on the machine and build flags. An untested middle ground is a "C/C++ lite" row with only #include edges and top-level functions and structs.
