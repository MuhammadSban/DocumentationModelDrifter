Deterministic tooling

Rebuild the models from the code, compare them with the committed /models.

That is the whole product. drifter keeps three architecture models (structural, behavioral, ownership) beside the code and, on every check, answers one question: do they still describe it? Try it on a tiny repository below. The answer is computed by this page with the same rules as Source/drifter/check.py.

    Chapter 1
    
The problem and the answer

    
Question: what does the tool promise, and what shape is its answer?

  

  

    
Architecture changes between commits are normal, but they happen silently. Reviews and separate documents miss them, the documented architecture drifts from the code, and people end up re-reading the code to learn what is true. The users are engineering and compliance teams at general-purpose AI model providers. They must keep technical documentation current, which is EU AI Act Article 53(1)(a).

    
drifter keeps that documentation as three models committed in /models, each the smallest representation that answers one question. That idea comes from the MAGE method the spec cites:

  

  

    

      
ModelQuestion it answersHow a check treats itOwner

      
        
structural.jsonWhat exists, and how do the parts relate? Modules, classes, functions, methods; imports and inherits edges.Regenerated from the code and diffed by element idEnrique

        
behavioral.jsonWhat may happen, in what order? States a variable takes and the transitions between them.Regenerated from the code and diffed by element idBarshan

        
ownership.jsonWho may change what? An ordered list of path rules, first match wins.Never regenerated. Each commit in the push is judged against the rules.Muhammad

        
scope.jsonNot a model: which files feed the two generators.Read first; picks the inputCore (Kaan)

      
    

  

  

    
The core idea, in one picture. A check never asks "is this code good?". It asks whether two descriptions of the same commit agree. One is fresh: rebuilt from the code right now. The other is committed: what a person last reviewed and accepted. Ownership is the odd one out. Who wrote a change is not visible in the code, only in the commits, so it is judged commit by commit instead of rebuilt.

  

  
  

    
Every check ends in one of three ways. The answer always has the same four fields, keys sorted, written as canonical JSON:

  

  

    
{
  "aligned": false,        // true only when all three lists are empty
  "behavioral": [],
  "ownership": [],
  "structural": [
    {"change": "ADDED", "file": "src/shop/orders.py",
     "id": "shop.orders:refund", "kind": "function"}
  ]
}

    

      

        
VerdictCLI exitHosted /analyze

        
          
aligned0200, drift.aligned: true

          
drift1200, drift.aligned: false

          
no verdict2200, drift: null plus a drift_error code

        
      

    

  

  

    
A difference means the code and the documentation disagree, not that the code is wrong. A person either fixes the code or accepts the drift by committing updated models, and git history records who accepted it and when. drifter never commits anything. init and update write files into your working copy for you to review, check only reads, and the hosted service never touches the repository at all.

    Chapter 4
    
Birth: drifter init

    
Question: how does a repository get its first /models, and where can init stop?

  

  
init is the arrow No models → Proposed. It runs once per repository, writes a draft and checks nothing. Structural and behavioral come from the code at the commit. Ownership is proposed from the git history up to it. scope.json gets the defaults. The hosted POST /system/generate runs the very same generate_models on a fresh clone and returns the four files instead of writing them.


  

    

      

        
        
        
        
      

      

    

    
    
      
  1. 1
    Overwrite guardAny of the four files already in /models and no --force: stop, exit 1, nothing written.
    2. 
      
  2. 2
    Resolve the commitThe given commit or HEAD, to its full SHA.
    3. 
      
  3. 3
    Pick files with the default scopeEvery .py file except under the top-level tests/. A nested src/tests/ stays in.
    4. 
      
  4. 4
    Read every file, then check each one parsesSize, then UTF-8, then pinned CPython ast, in path order. Parsed, never run.no verdict, exit 2: FILE_TOO_LARGE, PARSE_FAILED
    5. 
      
  5. 5
    Generate structural and behavioral; propose ownershipOwnership walks the whole history up to the commit. Each file still present gets one exact-path rule owned by the authors of its 10 newest commits. Merges, bots and sweeps over 50 files do not count toward the 10. Vendored folders and /models itself get no rule.
    6. 
      
  6. 6
    Write all four filesBuilt in memory first, so a stop leaves /models as it was. Canonical JSON, exit 0.
    7. 
      
  7. 7
    A person reviews, corrects ownership.json, commitsProposed becomes Baselined. That commit is the human decision on record.

Later, drifter update is the way to accept drift. It rewrites only structural.json and behavioral.json, using the committed scope. Your hand-corrected ownership.json and scope.json are left alone.







  

    Chapter 5
    
One check, end to end

    
Question: what happens between a request and the four-field answer, and where can a check stop?

  

  

    
A check can stop early in two different ways, and the difference matters to whoever reads the result.

    
    
      
  • HTTP error: "we could not look." The request was malformed, the repository or commit does not exist, git ran out of time, or the result could not be saved. The reply is 400, 404 or 500 and nothing is saved. Fix the request or retry.
    • 
      
  • No verdict: "we looked, but cannot judge." The commit was read fine, but it is in a state the check cannot compare: /models is missing or broken, or a file is too big or not Python. The reply is still HTTP 200 and the run is saved with drift: null and a drift_error code; the CLI exits 2. Fix the repository.
    • 
    

    
Either way, a check that did not finish is never reported as aligned. Pick a scenario to see where it stops.

  

  

    

      Completes
      
      
      
      HTTP error, nothing saved
      
      
      
      
      
      
      No verdict, HTTP 200
      
      
      
      
    

    

      
    
      
    
    
    
  
    
  
    Steps tagged hosted run only behind /system. The CLI enters at "Resolve" with a LocalReader and leaves at "Answer". Everything between is the same code.
    

    



    
  
    
    Chapter 6
    
    Inside the core: three seams
    
    
    Question: where are the boundaries that let four people build the core in parallel?
    
  
    
  
    
    
    A seam is a place where two parts meet through a small, fixed promise: a function signature and a data shape. Anything behind the promise can be rewritten without the other side noticing. That is what lets Enrique change how structural ids are built, or the hosted service change how it downloads files, without touching the core.
    
    
    The core is small: check.py is about 450 lines. It stays small because it talks to everything else through just three seams. The next three chapters open one each.
    
  
    
  
    
    
    
      
    Readers
    
      
    class Reader(Protocol):
    head: str
    def tree() -> {path: blob}
    def read(paths) -> {path: bytes}
    def log() -> str  # base..head
    
      
    The core relies on: four calls, one commit.
    
      
    Hidden: local or remote, clones, partial fetches, timeouts, the deadline, how blobs get there.
    
      
    Chapter 7
    
    
    
    
    
      
    Generators
    
      
    def generate_structural(
    files: dict[str, str]) -> dict
def generate_behavioral(
    files: dict[str, str]) -> dict
    
      
    The core relies on: purity, and the element rule (every element has a unique id, a kind and a file).
    
      
    Hidden: kinds, id scheme, attributes, mining rules, schema. All of it belongs to the model's owner.
    
      
    Chapter 8
    
    
    
    
    
      
    Comparison
    
      
    differences(fresh, committed)
  -> [{change, file, id, kind}]
check_ownership(rules, commits)
  -> [{author, change, commit,
       owners, path}]
    
      
    Callers rely on: the contract's ModelDifference and OwnershipViolation shapes, sorted.
    
      
    Hidden: how elements are indexed; the glob dialect.
    
      
    Chapter 9
    
    
    
  
    
  
    
    
    One choice holds the seams together. The core diffs every model the same way, by element id, instead of each owner writing a diff. The tester compares the diff byte for byte with the expected answers, order included. Three diff implementations would mean three chances to sort differently. The core also checks that every file parses before any generator runs. That way PARSE_FAILED and FILE_TOO_LARGE fire in one place, for the first bad file in path order, and the same broken file gives the same error whichever generator would have hit it first. Each generator then parses again with the same parser, and may assume it succeeds. These are phase4.md decisions Q1 and Q2.
    
  
    

    



    
  
    
    Chapter 7
    
    Reading a commit
    
    
    Question: how does one check get every file it needs, within the 80 s deadline, without running any of it?
    
  
    
  
    
    
    read_sources(reader) gathers everything before any model is built, in this order:
    
    
      
      
    1. List the tree: every file path at the commit, with no contents yet.
      2. 
      
    2. Read and validate the four /models files: JSON, then the owner's schema, the element rule, scope, ownership rules.
      3. 
      
    3. Read the in-scope code files. This has to wait for step 2, because scope.json is what says which files those are.
      4. 
      
    4. Read the commit log base..head, for the ownership check.
      5. 
    
    
    
    The hosted service has to do this over the network, which is where time goes. Its trick is a blobless clone. Git stores a commit as three kinds of object: the commit, folder listings ("trees") and file contents ("blobs"). A blobless clone downloads only the first two, which is small and fast, so the reader can see every path before deciding which contents to ask for. It then asks for all of them in one request. Two implementations sit behind the same protocol:
    
  
    
  
    
    
    
      
    LocalReader, for the CLI
    
      Source/drifter/check.py
      
      
        
    1. git rev-parse the head; the base defaults to its first parent
      2. 
        
    2. git ls-tree -r -z --full-tree, regular files only
      3. 
        
    3. all blobs in one git cat-file --batch process
      4. 
        
    4. git log -z --name-status -M for base..head
      5. 
      
    
    
    
    
    
      
    Comparison, for the hosted service
    
      Source/GitHub_Connector/fetch.py
      
      
        
    1. git clone --filter=blob:none --no-checkout: commits and folder listings only
      2. 
        
    2. git ls-tree at the commit
      3. 
        
    3. one batched git fetch --stdin per read: /models, then the in-scope files
      4. 
        
    4. cat-file with GIT_NO_LAZY_FETCH=1, so a missing blob is an immediate 500, never a slow crawl
      5. 
        
    5. temporary clone deleted when the check ends
      6. 
      
    
    
    
  
    
  
  
    
    
    Deliberately left out, each needing a conscious decision: a retry when the batch download is cut off, a GitHub token for higher rate limits, a clone cache per repository, and spotting a file over 1 MB before downloading it. A blobless clone cannot report sizes without fetching, so size is judged after the download.
    
  
    

    



    
  
    
    Chapter 8
    
    The models and their owners
    
    
    Question: what does each model file hold, and what must every generator promise?
    
  
    
  
    
    
    Each owner decides everything inside their model. The core relies on two rules only.
    
    
      
      
    • The element rule. Every top-level list holds elements. Each element has an id that is unique in the whole model, a kind, and the in-scope file it comes from. Every other field is an attribute. A value that is not a list, such as schema_version, is not diffed.
      • 
      
    • Purity. No git, network, clock, randomness or environment. Never import or run the analysed code. Sort each list by id and leave out line numbers, so moving code is not drift. The output is byte-identical on Linux and Windows.
      • 
    
    
    
    A committed model is validated against its owner's *.schema.json beside the generator; breaking it gives INVALID_MODELS. The shared seam test in tests/common/test_seam.py holds every generator to both rules.
    
  
    
  
    
    
    
      
      
      
      
    
    
    
    
  
    

    



    
  
    
    Chapter 9
    
    Deciding a difference
    
    
    Question: when is an element ADDED, REMOVED or MODIFIED, and when is a commit an ownership VIOLATION?
    
  
    
  
    
    
    
      
    Structural and behavioral: per element id
    
      Is the id in the committed /models?
      
    noADDED in the code, not in the model
    
      
    yes, and is it in the fresh model from the code?
        
    noREMOVED in the model, not in the code
    
        
    yes, and are all fields equal?
          
    noMODIFIED same id, fields differ
    
          
    yesaligned no entry
    
        
    
      
    
      
    Reported from the code's side and sorted by id. An id that encodes its identity parts, such as a behavioral guard, turns a change into one REMOVED plus one ADDED, never MODIFIED.
    
    
    
    
    
      
    Ownership: per non-merge commit in base..head
    
      For each path the commit changes (a rename: its old path)
      
    first rule whose pattern matches?
        
    noneopen to anyone no entry
    
        
    found: is the author's email among its owners?
          
    yesowner no entry
    
          
    noVIOLATION names commit, path, author, owners
    
        
    
      
    
      
    Why ownership is never regenerated: history grows with every push, so re-mining it would make anyone new touching a file look like drift.
    
    
    
  
    

  
    Everything hangs on the id
    
  
    The left tree only works because an element's id is built from what it is, never where it sits. So the same everyday edit can land in any of the three outcomes, depending on whether it touches the id or only the fields beside it:
    
  
    
    
    
      
    You changeThe element's idReported as
    
      
        
    Move Order.cancel lower in the file, or edit a commentunchanged: ids hold no line numbersno entry
    
        
    Add a parameter to Order.cancelunchanged: shop.orders:Order.cancelMODIFIED its params differ
    
        
    Rename cancel to voidthe old id disappears, a new one appearsREMOVED + ADDED
    
        
    Change a guard from 'open' to 'new'a transition's id contains its statesREMOVED + ADDED
    
        
    Change what a method does, with no new state or signatureunchanged: bodies are not modeledno entry
    
          
    
    
  
    
  
    The last row is the honest limit: the models describe shape and states, not behaviour line by line. A rewrite that keeps every name, signature, import and string state is not drift.
    

  
    Try the ownership checker
    
  
    This runs a port of check_ownership and of the shared glob from models/common.py. In that glob, **/ is zero or more folders, ** is anything, * is one path segment's text and ? is one character. scope.json, ownership rules and the pod's mapping-v1.1.yaml all use this one matcher, so a pattern means the same thing everywhere.
    
  
    
    
    
      
    
        
        
        
    One rule per line. Order matters: the first match wins.
    
      
    
      
    
        
        
      
    
      
    
        
        
        
    Compared in lowercase.
    
      
    
      
    
    
    
    
      
      
      
      
      
      
    
      
  
      

      



      
  
      
    Chapter 10
    
      The hosted service
      
    
      Question: what does the hosted service add around the core, and why?
      
  
      
  
      
    
      One FastAPI app (GitHub_Connector/api.py) on Railway serves four things: the pod contract's API under /system, the course's test-session routes, our own tester under /tester, and a console at /. Every push to main deploys, and /system/health's tool_version names the deployed commit.
      
    
      The contract is shared with Team 16, so /analyze answers two different questions in one reply. They are easy to confuse:
      
    
        
      
      • Change detection, the pod's shared layer: which files changed between base and head, and what kind of file is each? It compares two commits and classifies paths with mapping-v1.1.yaml. It knows nothing about models.
        • 
      
      • Drift, Team 15's optional drift key: does /models still describe the code at head? It looks at one commit's full contents, not at a diff, and carries the core's four-field answer.
        • 
    
      
    
      Both run on the same clone. Team 15 has no prose detector, so issues is always []. That is contract deviation 1.
      
  
      
  
      
    
      
      
      RouteWhat it doesBehind it

      Concurrency and time
      
      
      A bounded semaphore admits at most 2 analyses. The 80 s deadline starts once a slot is free and caps every git call (each also capped at 60 s). It stays under the tester's 90 s per call.
      
    
      
    
      
      
      Durable, write-once results
      
      
      runs.py writes each result once, to a temp file and then os.replace, on a Railway volume. On Railway without a volume, the app refuses to start rather than silently lose results. That is decision D6, and runs.py is the only file a different store would change.
      
    
      
    
      
      
      One error table
      
      
      Every failure goes through STATUS_FOR: INVALID_REQUEST 400; REPOSITORY_NOT_FOUND, COMMIT_NOT_FOUND, ANALYSIS_NOT_FOUND 404; ANALYSIS_FAILED, STORAGE_FAILED 500. FastAPI's 422 is reworded as 400.

    Chapter 13
    
      Glossary
      
    
      Question: what do the project's words mean, exactly?
      
  
      
  
      
    
      Models
      The files in /models that describe the code's structure, behavior and ownership. This system's documentation.
      
    
      Drift
      A difference between what the code is and what the models say it is. Not "issue" or "finding"; those are the pod's prose findings.
      
    
      Element
      One thing the structural or behavioral model describes, such as a class, an import or a transition. It has an id that stays the same while the thing does.
      
    
      Accepting drift
      A person committing updated models after a false verdict. The git history of /models records who and when.
      
    
      Element id
      The name that says which thing an element is, built from what it is and never from where it sits: shop.orders:Order.cancel, imports:shop.orders->shop.models. The diff matches elements by id alone.
      
    
      Baseline
      The /models a person last committed. Every check compares against it; accepting drift replaces it.
      
    
      Scope
      scope.json: include and exclude patterns that pick which files feed the two generators. Not a model, never diffed. Ownership ignores it.
      
    
      Base and head
      Head is the commit being checked. Base is where the push started, by default head's first parent. Only the ownership check uses base: it judges the commits base..head.
      
    
      Seam
      A boundary where two parts meet through a small fixed promise (a signature and a data shape), so each side can change behind it.
      
    
      Blobless clone
      A git clone with commits and folder listings but no file contents. The hosted reader then downloads exactly the contents it needs, in one batch.
      
    
      Fresh model
      The model regenerated from the code at the commit being checked.
      
    
      Committed model
      The model as it sits in /models at that commit: the baseline a person accepted.
      
    
      No verdict
      A check that could not decide: drift: null, a drift_error code (MODELS_NOT_FOUND, INVALID_MODELS, FILE_TOO_LARGE, PARSE_FAILED), and CLI exit 2.
      
    
      Acceptance criterion
      One of the pod's checks AC-01 to AC-10, with the pod's meaning. AC-11 is this system's own and counts as AC-02.
      
    
      Pod, contract
      Teams 15 and 16 share a contract in docs/contract/: routes, JSON, the test list and fixtures. Team 15 adds drift, drift_error and /generate as optional features.
      
    
      MAGE
      The modeling method the spec cites. Each model answers one question with the smallest representation that does, and every model has a check that keeps it true to the code.
