Q1 COMMON PROBLEM SELECTION
====================================================================================================

1.1 SELECTED PROBLEM

The users of Documentation Tracker are engineering and compliance teams at general-purpose AI model
providers, who must keep technical documentation accurate as the model's design and architecture
change. Current approaches rely on manual reviews and separately maintained documents. These can
miss changes made in commits and pull requests, and make documentation hard to trace to a
particular version.

Documentation Tracker keeps three machine-readable models of the system's design in the repository,
next to the code: what parts exist and how they relate (structural), which states the system can
move through (behavioral), and who is responsible for each part (ownership). A GitHub Action checks
on every push, read-only, that the code still matches the models. A mismatch is reported for a
person to resolve. Each check leaves a record linked to its commit, and the history of /models
records every design change a person accepted.

This supports the obligation in Article 53(1)(a) of the EU AI Act to keep technical documentation
current and supply it to authorities on request [1]. Of the content Annex XI requires, the models
cover the code side of the system's design: architecture (1(d)), the technical means to integrate
the model (2(a)), and design specifications and key design choices (2(b)) [5]. Training data,
computational resources and energy use (2(c) to 2(e)) are out of scope. The tool supports keeping
documentation current; it does not write the documentation or certify compliance. (The specific
Annex XI items are open, see Q11.)

1.2 SELECTION RATIONALE

Documentation Tracker keeps technical documentation current with a focused GitHub workflow,
combines deterministic checks with human review, leaves significant judgments to people, and
avoids external LLM costs and confidentiality concerns. It shares a general
approach with Matt Pocock's code-review skill, which compares code changes against documented
standards and specifications [2].

The project requires real engineering decisions: what facts to extract from code, how to handle
commit history, how to keep false alerts low, and how to retain traceable evidence. Each team builds
its own implementation of the shared format, and both are compared on the same labelled commits by
accuracy, false-alert rate, coverage and execution time.

The approach follows MAGE [3]: a model is the smallest representation that answers one engineering
question, and keeping models and code in step (correspondence) is enforced by a gate rather than by
hand. For a repository with existing code and settled intent, MAGE's starting move is recover,
reconcile, govern: generate the models, let people correct them, then check every change against
them.

Q2 COMMON SCOPE
====================================================================================================

2.1 SYSTEM BOUNDARY

  Outside: developer (runs drifter init and update locally, commits /models, reviews pull requests)
  Outside: GitHub Action (runs drifter check on its own checkout on every push)
  Outside: cross-team tester and other API callers (call the hosted service)
        |
        |  in: repository + commit (code, /models and git history are read at that commit)
        v
  Inside:  drifter, one codebase run by the CLI, the Action and the hosted service:
           GitHub integration -> three generators -> comparison -> verdict
        |
        |  out: verdict JSON (true or false, differences per model) and, from the CLI, an exit code
        v
  Outside: the analysed repository, read-only. The tool never writes to it, /models included.

2.2 SCOPE

Included scope
--------------

  * Generate the three models of a repository as canonical JSON (drifter init), and regenerate
    them after an intended change (drifter update). The developer commits them to /models.
  * On each push, check the code at that commit against the committed /models (drifter check) and
    return true or false with the differences.
  * Report every changed file with its change type, as input to the ownership check and the report.
  * Return results in a shared JSON format: repository, commits, verdict per model, differences and
    skipped files, so both teams' outputs can be validated automatically.
  * Keep each check's result as a retrievable record (REQ-04).

Excluded scope
--------------

  * Version control systems other than Git.
  * Models or documentation stored outside the repository.
  * Prose documentation (README, docs/*.md) is not analysed (open, see Q11).
  * Judging whether the code is correct, or whether a design change is a good idea. The tool only
    says that code and models disagree.
  * Writing to the analysed repository, including /models.
  * Decision, measurement and provenance models.
  * LLMs or any generative model at runtime.
  * Durable storage for verdicts beyond what REQ-04 names.
  * A full custom GitHub-style graphical interface.

Operating limits and assumptions
--------------------------------

  * Intended users are engineering and compliance teams at general-purpose AI model providers.
    Authorized reviewers remain responsible for compliance judgments.
  * The hosted service supports public GitHub repositories. The CLI and the Action work on any
    checkout. Code and /models live in the same repository.
  * The first version supports Python source only. Files are read as text and parsed, never
    imported or executed. This specification names no parser: each team chooses its own, and each
    release pins its parser and Python version.
  * Both teams use the common input and output formats in Section 5.
  * Testing uses small repositories provided by the pod.
  * Limits: 120 s per check, 60 s per git call, at most 2 checks at once in the
    hosted service. Files over 1 MB, binary files and files that are not UTF-8 are skipped and
    listed. Hidden paths, symlinks and submodules are ignored.

Q3 COMMON SPECIFICATION
====================================================================================================

3.1 REQUIREMENTS

REQ-01 - Detect changes
-----------------------

Given a Git repository, a commit and an optional base commit, the system shall use read-only
analysis to list every changed file with its change type. Engineering teams need to know what moved
before they can judge whether the design moved.

REQ-02 - Flag drift between the code and its models
---------------------------------------------------

The system shall regenerate the structural and behavioral models from the code at the commit and
compare them with the committed /models by element id. It shall check every non-merge commit
between the base and the commit against the ownership rules. Each difference shall name the model,
the change (ADDED, REMOVED, MODIFIED or VIOLATION), the element id or path, and the file. For each
model the verdict also says whether it is empty (3.2). The verdict is true only when all three
models are aligned. Supports the documentation maintenance obligation in Article 53(1)(a) and the
design content in Annex XI.

REQ-03 - Keep people in charge of accepting drift
-------------------------------------------------

A false verdict asks a person for a decision and is never resolved by the tool. A person accepts
drift by committing updated /models; until then the code must be fixed instead. That commit, with
its author, timestamp and review in the pull request, is the review record. The verdict names the
commit that last changed /models, so each verdict can be traced to the person who accepted the
baseline. The system shall not approve or modify code or models on its own. Whether the check
blocks a merge or only warns is the repository owner's choice.

REQ-04 - Preserve traceable evidence
------------------------------------

Each check shall produce a JSON verdict with the repository, the commits checked, the /models
commit, the verdict and the differences. The GitHub Action uploads it as a workflow artifact (kept
90 days by default) and writes it to the job summary. The hosted service saves each verdict it
produces, retrievable by id until the service restarts. The git history of /models is the durable
record of every accepted design change. Together these support responses to Commission requests
under Articles 91 and 53(1)(a).

REQ-05 - Handle invalid inputs and incomplete checks explicitly
---------------------------------------------------------------

When inputs are missing or invalid, the repository or commit cannot be accessed, /models is missing
or malformed, an in-scope file cannot be parsed, or the check fails, the system shall return an
error and a short message. It shall never return true or false for a check it could not complete.
Users must be able to tell a successful check from one that could not be done.

REQ-06 - Protect repository content
-----------------------------------

The system shall treat the repository as read-only input, shall not execute or import its code,
and shall not write to it, /models included. Engineering teams need checks that cannot alter their
code.

REQ-07 - Provide deterministic, testable results
------------------------------------------------

Each implementation shall accept requests and return JSON through the common interface in Section
5. Given the same repository version, /models and tool version, repeated runs shall return
byte-identical models and an identical verdict and differences. Only the analysis id and the
creation time may differ. Both teams' implementations shall produce the same models for the same
commit.

Categories that do not apply
----------------------------

Physical safety, hardware control and hard real-time response do not apply: the system analyses
repository content and controls nothing physical. Full software-correctness verification and
legal-compliance certification are excluded.

3.2 THE THREE MODELS AND THE SYSTEM MODEL

The product's models
--------------------

/models holds four files: structural.json, behavioral.json, ownership.json and scope.json.

The model format is shared by the pod, because /models is an input both teams' systems must read
and both must answer the same way [6]. The JSON Schemas, element kinds, id scheme and mining rules
are pod decisions (open, see Q11). Each team writes its own code to produce them.

  Structural
    Question:   What exists, and how do the parts relate?
    Contents:   to be agreed in the pod (open, see Q11).
    Comparison: regenerate at the commit, then set difference by element id.

  Behavioral
    Question:   What may happen, and in what order?
    Contents:   to be agreed in the pod (open, see Q11).
    Comparison: regenerate at the commit, then set difference by element id.

  Ownership
    Question:   Who may change what?
    Contents:   rules. Each rule is a path pattern and its owners, given as git author emails.
                Rules are tried in order and the first match wins. A path no rule matches is
                open to anyone.
    Source:     drifter init proposes a first file from git history (how, open, see Q11).
                People then correct it by hand, like a GitHub CODEOWNERS file.
    Comparison: not regenerated per push. Every non-merge commit between the base and the
                checked commit is judged: each file it changes must have, as its git author, one
                of the owners of that file's path. Co-authors do not count, and bots get no
                special case (list a bot's email to allow it). A violation names the commit,
                the path, the author and the owners.

Why ownership is checked differently: it is mined from history, and history grows with every push,
including the push being checked. Regenerating and comparing it would fail whenever someone new
touched a folder, whether or not anything was wrong. Checking authors against rules answers the
ownership question directly: was this change made by someone allowed to make it?

Scope. scope.json holds include and exclude path patterns. It decides which files feed the
structural and behavioral generators; drifter init writes the defaults, include **/*.py and exclude
tests/**. Ownership rules apply to every path, whatever the scope says. Editing the scope without
regenerating the models shows up as drift by itself. The pattern rules for scope.json and
ownership.json must be identical in both teams (open, see Q11).

Layout of every model file, so that both teams produce the same bytes:

  * Keys sorted; 2-space indent; UTF-8 with non-ASCII characters written as they are, not escaped.
  * LF line endings and exactly one trailing newline.
  * Lists sorted by element id.
  * No timestamps, absolute paths or line numbers, so moving code without changing it is not drift.
  * A schema_version field; a schema change bumps the version.

Differences are reported from the code's side:

  ADDED      in the code but not in the model
  REMOVED    in the model but not in the code
  MODIFIED   the same id in both, with different attributes
  VIOLATION  ownership only: a commit changed a file its author does not own

Empty models. For the structural and behavioral models, "empty": true means the committed model
and the freshly generated one both have no elements, so "aligned" is necessarily true. If only one
side is empty, the code gained or lost elements: "aligned" is false and the differences list them.
For ownership, "empty": true means ownership.json has no rules, so every path is open. The flag
lets a reader tell "true because nothing is modelled" from "true because the code matches".

The system model
----------------

The lifecycle of a repository under the tool, drawn in docs/models/behavioral-model.png. Its source:

    stateDiagram-v2
        accTitle: Lifecycle of a repo under DocumentationModelDrifter
        accDescr: The tool proposes three models once, the user commits them as the baseline,
                  and every push is then checked against them, ending true, false or in an error.

        state "No models" as NoModels

        [*] --> NoModels
        NoModels --> Proposed: init generates the 3 models
        Proposed --> Baselined: user reviews, corrects, commits /models
        Baselined --> Checking: push

        state Checking {
            [*] --> Fetch
            Fetch --> Generate: code + diff at head
            Generate --> Compare: 3 fresh models
            Compare --> [*]
        }

        Checking --> Aligned: all 3 models match
        Checking --> Drifted: any model differs
        Checking --> Failed: fetch or parse error

        Aligned --> Baselined: true, green check
        Failed --> Baselined: error, no verdict, baseline kept
        Drifted --> Checking: push a code fix or updated /models

(Mermaid needs accDescr on one line; it is wrapped here only to fit this file.)

3.3 MODEL EXPLANATION

The tool proposes models once. A person reviews and corrects them, then commits them as the
baseline. After that, every push is checked and ends in one of three states. Only Drifted needs a
person, who either fixes the code or commits updated models in the next push. A Failed check gives
no verdict and leaves the baseline as it was. An in-scope file that cannot be parsed fails the
check (PARSE_FAILED) instead of being skipped: a skipped file's elements would vanish from the
fresh model and show up as REMOVED drift that is not real. The check compares the facts in the code
with the facts in the models.

Q4 ACCEPTANCE CRITERIA
====================================================================================================

4.1 REQUIREMENT COVERAGE

  * AC-01, REQ-01: On a labelled test repository, the system finds every changed file with the
    right change type. Checked automatically.
  * AC-02, REQ-02: A commit changes what a structural or behavioral model describes without
    updating /models. The verdict is false and names the right model, exact element id and file.
    Checked automatically.
  * AC-03, REQ-02 and REQ-07: A commit changes only comments and whitespace, or changes the code
    together with matching updated /models. The verdict is true. Checked automatically.
  * AC-04, REQ-03: After a false verdict, the code and /models are unchanged and the tool has made
    no commit. Checked automatically and by inspection.
  * AC-05, REQ-03: Committing updated /models after a false verdict makes the next check true, and
    the verdict's /models commit gives the person who accepted it and when. Checked automatically.
  * AC-06, REQ-04: Each check through the hosted service saves a separate JSON record with the
    repository, commits, /models commit, verdict and differences, and fetching it by id returns it
    byte for byte while the service runs. Each Action run uploads its verdict as an artifact.
    Checked automatically.
  * AC-07, REQ-05: A request without a commit id returns 400 with a message saying what is missing,
    and no verdict. Checked automatically.
  * AC-08, REQ-05: An unknown repository or commit returns 404 with a message. A commit with no
    /models, or an in-scope file that cannot be parsed, returns an error, never true or false.
    Checked automatically.
  * AC-09, REQ-06: The repository is byte-identical before and after a check, and none of its code
    runs. Checked by automated tests and inspection.
  * AC-10, REQ-07: Three runs with the same repository, commit, /models and tool version return
    byte-identical models and an identical verdict and differences, and generate at the baseline
    returns the committed /models byte for byte on either team's system. Checked automatically.
  * AC-11, REQ-02: A commit by someone who is not an owner of a changed path gives false, naming
    the commit, path, author and owners; the same change by an owner gives true. Checked
    automatically.

Q5 CROSS TEAM TESTING INTERFACE (TEAM 15 PROPOSAL FOR THE POD)

5.1 INTERFACE CONTRACT

All routes sit under /system.

  POST /system/generate        REQ-01, REQ-06, REQ-07
    Takes a request (below) and returns the three models for that commit. Writes nothing.
    200 with the models; 400, 404, 422 or 500 with an error body.

  POST /system/compare         REQ-01, REQ-02, REQ-04, REQ-05, REQ-07
    Takes a request and checks the code at that commit against the /models committed there.
    200 with the verdict, which is saved; 400, 404, 422 or 500 with an error body, and nothing
    saved.

  GET /system/analysis/{analysis_id}       REQ-04, REQ-07
    Returns a saved verdict byte for byte. 200, or 404 if the id is unknown. Changes nothing.

  GET /system/health
    Reports that the service is up.

  POST /system/test/setup and GET /system/test/report
    The course's system endpoints (docs/base/student-facing-spec.docx.pdf).

Errors are {"code", "message"}:

  400 INVALID_REQUEST          a field is missing or malformed
  404 REPOSITORY_NOT_FOUND     the repository does not exist or is not public
  404 COMMIT_NOT_FOUND         the commit cannot be found
  404 MODELS_NOT_FOUND         compare only: the commit has no /models, or a file in it is missing
  404 ANALYSIS_NOT_FOUND       no saved verdict has that id
  422 INVALID_MODELS           compare only: a file in /models fails its schema
  422 PARSE_FAILED             an in-scope file cannot be parsed; the message names file and line
  500 TIMEOUT                  the check ran past its deadline
  500 WRITE_FAILED             the verdict could not be saved
  500 INTERNAL_ERROR           anything unforeseen

The 422 codes cover a valid request whose repository content cannot be checked.

Exit codes of drifter check, which the GitHub Action passes or fails on:

  0   true: all three models aligned
  1   false: drift found
  2   error: no verdict (any of the errors above)

5.2 DATA SCHEMAS AND EXAMPLES

The request: repository as "owner/name", commit_id as 7 to 40 hex characters, and an optional
base_commit (default: the commit's first parent).

    {
      "repository": "owner/name",
      "commit_id": "7fd1a60"
    }

a pod decision.

    {
      "analysis_id": "an-<32 hex>",
      "repository": "owner/name",
      "head_commit": "<40 hex>",
      "base_commit": "<40 hex>",
      "models_commit": "<40 hex, the commit that last changed /models>",
      "tool_version": "<version>",
      "aligned": false,
      "models": {
        "structural": {
          "aligned": false,
          "empty": false,
          "differences": [
            {"change": "ADDED", "kind": "node", "id": "shop.orders:Order.cancel",
             "file": "src/shop/orders.py"}
          ]
        },
        "behavioral": {"aligned": true, "empty": true, "differences": []},
        "ownership":  {"aligned": true, "empty": false, "differences": []}
      },
      "changes": [
        {"path": "src/shop/orders.py", "old_path": null, "change_type": "MODIFIED"}
      ],
      "skipped": [],
      "created_at": "<ISO 8601 UTC with milliseconds and Z>"
    }

An ownership difference:

    {"change": "VIOLATION", "commit": "<40 hex>", "path": "src/payments/charge.py",
     "author": "barshan@example.com", "owners": ["kaan@example.com"]}

A generate response returns {repository, head_commit, tool_version, models: {structural,
behavioral, ownership}}, each model in the shared format of 3.2.

An invalid request, missing the commit id:

    {"repository": "owner/name"}

returns 400:

    {"code": "INVALID_REQUEST", "message": "commit_id is required"}

5.3 REPEATABLE TEST SETUP AND THE TESTING CONTRACT

Both teams are tested at their base URL against the same test repositories. The labelled commits
in 4.2 fix the expected verdicts before anything runs. The service is stateless for testing: no
login, and no reset between tests. Controlled examples come first, then real Python codebases to
see how well the generators describe real code.

The course's Cross-team Testing Interface [6] fixes the testing routes and the report; the pod
defines everything the tester does in between.

Fixed by the course
-------------------

  * Tester: POST /test/setup {target_url} returns 201 {session_id}; POST /test/run {session_id}
    returns the suite report; GET /test/report?session_id= returns the stored report.
  * System: POST /test/setup {session_id, setup} returns 201 {session_id};
    GET /test/report?session_id= returns code coverage since setup.
  * Report: every planned test exactly once, each with an outcome of pass, fail, error or skip,
    and code, component and system coverage.

Defined by the pod
------------------

  * Project API: the routes in 5.1.
  * Setup data: {}. The fixture repository is public and fixed, so the system needs no starting
    data, and project requests do not carry the session id. Code coverage counts the lines run
    since setup.
  * Fixture and expected answers: one public fixture repository with the labelled commits of 4.2,
    and one shared file of expected answers that both testers read, built by both teams (4.2).
  * What a test checks: per model, "aligned" and "empty"; for each expected difference, its exact
    element id (or path, for ownership), its change and its file. T-17 checks that generate at the
    baseline returns models byte for byte equal to the /models committed there, which proves both
    teams mine the same way.

Q6 MILESTONES FOR PHASES 4 AND 5
====================================================================================================

6.1 PHASE 4

Capability: generate the three models and check a commit against them.

Artifacts: structural, behavioral and ownership generators; comparison; orchestrator; the drifter
command line tool (init, update, check); the shared JSON Schemas; the labelled test repository; pod
agreement on Section 5 and on the model format.

Uncertainty reduced: whether the models capture design changes people care about without flagging
noise (Risk 1, 9.1), and whether two implementations of one format agree (Risk 4).

Demonstration: run drifter init on the test repository, push L2 and get false naming the new
function, then push L5 and get true.

Automated validation: AC-01, AC-02, AC-03, AC-07, AC-08, AC-10, AC-11.
Requirement coverage: REQ-01, REQ-02, REQ-05, REQ-07.

6.2 PHASE 5

Capability: the check runs on every push and its record can be found later.

Artifacts: a tagged release that installs with pip and the reusable workflow at that tag; the
hosted generate and compare routes; the tester running the labelled cases; verdicts saved as
workflow artifacts and by the hosted service.

Uncertainty reduced: the whole loop works end to end without the tool ever writing to a repository.

Demonstration: on a public repository, push a change that drifts and see a red check; commit
updated /models and see a green check; open the run's verdict artifact and find, through its
/models commit, who accepted the change.

Automated validation: AC-04, AC-05, AC-06, AC-09, AC-10.
Requirement coverage: REQ-03, REQ-04, REQ-06, REQ-07.

6.3 SEQUENCING RATIONALE

Each phase needs the one before: the check cannot run without generators, and the gate cannot run
without the check. If time runs short, cut in this order: richer behavioral patterns, durable
storage for verdicts, a viewer. The generators, comparison, gate and review loop stay.

                                            non-merge commit's author email and changed files
  Structural generator           Enrique    files -> structural.json
  Behavioral generator           Barshan    files -> behavioral.json
  Ownership generator and check  Muhammad   history -> ownership.json; commits and authors ->
                                            violations
  Comparison                     open       baseline model and fresh model -> differences
  Orchestrator                   open       one request -> one verdict; calls the others in order
  Tester                         open       labelled commits -> the course's suite report

One codebase, three ways to run it, all through the orchestrator:

  * The drifter CLI on a developer's machine: init and update write models locally for the
    developer to review and commit; check prints the verdict and sets the exit code.
  * The GitHub Action: runs drifter check on its own checkout on every push, uploads the verdict
    as an artifact and writes it to the job summary.
  * The hosted /system API: serves generate and compare for course testing and other callers.

Generators are pure functions (files in, JSON out): no git, network, clock or randomness. Only the
GitHub integration runs git.

Adoption. A repository installs drifter with pip from the DocumentationModelDrifter GitHub
repository at a release tag, and adopts the check with one uses: line pointing at the reusable
workflow at that same tag. The tag is the tool version, so every run of one tag gives the same
result.

7.2 DESIGN DECISIONS

The models are a living map between documentation and code, and the check is fully
deterministic. The tool is not a wrapper around an LLM.

One infrastructure, separate implementations: both teams share the API, the model format and the
mining rules, and each writes its own code, parser included (1.3).

Human review is mandatory: only a person can accept drift (REQ-03). What is selectable is how
strongly the check is enforced in a repository, warn-only or a required check.

The developer writes /models; the tool only reads. Models use stable ids, never line numbers.
Ownership is a rule check, for the reason given in 3.2.

7.3 OPERATION AND OBSERVABILITY

The service is stateless: no accounts, no login and no job queue, and the repository holds
the models. It runs at most 2 checks at once, stops each check at its deadline, and reports
that it is up at GET /system/health.

Two measures show whether the check is useful: how often drift is accepted (updated /models)
rather than fixed in the code, and the false-alert rate on labelled no-drift commits.
Postmortems use precision and recall on planted changes.

7.4 VALIDATION STRATEGY

  * Golden tests per generator: small code snippets, each with its exact expected JSON.
  * The labelled cases in 4.2, run locally, in CI and by the tester against the deployed service.
  * A determinism test: the same commit gives byte-identical /models on Linux and on Windows.
  * A cross-team check: generate at the fixture baseline matches the committed /models on both
    teams' systems (T-17).
  * Tiny fixture repositories built with git init in tests, with scripted authors for ownership.

Q8 BUILD BUY AND REUSE
====================================================================================================

8.1 CAPABILITY DECISIONS

  * Change detection: reuse Git. The GitHub integration validates commits, extracts changes and
    handles failures without running repository code.
  * Model mining: build. Each team writes its own generators to the pod's shared format, with a
    parser of its choice, and maintains its generators and golden tests.
  * Workflow automation: reuse GitHub Actions. The Action is the main trigger, on every push, and
    runs the check on its own checkout. Standard runners are free for public
    repositories.
  * Distribution: reuse pip and GitHub release tags. No PyPI or Marketplace publishing.
  * Team process: reuse OpenSpec [4] for the team's own specs and tickets. Each ticket is an
    OpenSpec change whose scenarios are agreed before coding, and each scenario becomes one test.
    OpenSpec manages documents only and does not read code, so it is not part of the product.

8.2 GENAI USE

Claude and Codex assist development: code, tests, reviews and documents, with every result checked
by people and by the tests in Section 4. GenAI is not part of the running system, which keeps the
check repeatable and avoids runtime cost.

====================================================================================================
Q9 MAJOR RISKS AND INVESTIGATION PLAN
====================================================================================================

9.1 PRIORITY RISKS

Priority 1: noise
-----------------

The models may flag changes nobody considers design drift, such as renaming an internal helper. If
most red checks are noise, developers accept every change with update and the check loses its
value; AC-03 would also fail on real code. Investigation: plant known
changes in the test repository, some that change the design and some that should not, and measure.
Targets: at least 90 of 100 planted design changes flagged, and fewer than 10 of
100 no-drift commits flagged. Run it first in Phase 4. If the false-alert target fails, the pod
narrows the models through the scope or by dropping kinds of element.

Priority 2: behavioral coverage
-------------------------------

The behavioral model only captures the patterns the pod agrees on. A repository without them gets
an empty model ("empty": true) whose check is always true. Investigation: run the generators on the
fixture repository and on two or three real Python repositories in Phase 4. If most come back
empty, the pod decides whether to add a broader pattern.

Priority 3: determinism across environments
-------------------------------------------

Parser output can change between parser or Python versions, and path separators and ordering
differ between operating systems, any of which breaks REQ-07. Mitigation: each release pins its
parser and Python version, every file follows the layout in 3.2, and the determinism test runs on
Linux and Windows.

Priority 4: two implementations of one format
---------------------------------------------

Each team writes its own generators, so the two can disagree on edge cases. One disagreement makes
the other team's system report drift at the baseline and fail T-01 and T-17. Mitigation: shared
JSON Schemas, shared golden snippets with their expected JSON, and T-17 run by both testers.

9.2 RISKS REQUIRING POD AGREEMENT

  * The interface in Section 5.
  * The model format: JSON Schemas, element kinds, id scheme, mining rules and path pattern rules.
  * The testing contract in 5.3: setup data, test list, what each test checks, and the component
    and criteria lists. Both testers implement the same list.
  * The shared fixture: how the two teams split building it, with an expected verdict per model.
