Linters, tests and CI as Alignment: how MAGE sees checks

In MAGE (Davis, 2026), checks aren't hygiene. They are how an obligation stops depending on each future agent remembering it. Chapter 3 calls this Alignment, the partner of Modeling. Each section below covers one of its moves and applies it to DocumentationModelDrifter.

Alignment principleMake engineering obligations enforceable by encoding them into mechanisms that constrain actions, produce evidence, evaluate that evidence, and control admission.

§3.1Guidance is not enforcement

"Guidance improves the producer's odds; enforcement changes what admission must trust." MAGE counts an obligation as enforced only when the environment can block the action or reject the result.

Guidance

Shifts the odds

  • AGENTS.md today: "Verifiable goals … don't call it done until the checks pass"
  • Proposed AGENTS.md line (mage_take.md C9, not yet added): "Run pytest and drifter check before declaring a task done"
  • docs/agents/modeling.md house rules
  • Prompts, skills, examples

The agent can misread, forget or ignore any of these.

Enforcement

Changes what is admitted

  • A required ci / test status check on main
  • CODEOWNERS review on models/ownership.json
  • Harness permissions or hooks that refuse a tool call

These hold no matter what the agent believed. This repo has none of them yet.

§3.1–3.2Place each check at the earliest decidable boundary

There are four intervention boundaries. The rule is to place enforcement "at the earliest boundary where the obligation is both legible and decidable." Earlier means cheaper repair. Earlier than the property allows means false refusals. Pick a check to see where it belongs.

Placement and strength are separate decisions. A narrow permission at the action boundary can enforce more strictly than a late CI check. The boundaries aren't a scale from weak to strong.

Local hooks vs CI. A local git hook (pre-commit, pre-push) gives fast feedback but can be bypassed; hosted CI is "enforced for everyone." The course lecture puts it this way: "Local hooks are a convenience layer; CI is the control layer" (Building with Agents, deck 2-7, S20). So a hook can run ruff early, but the gate is the required CI check.

§3.2.1Agreement is not correctness

"Enforcement requires something against which the work can actually be wrong." MAGE separates three relations, and evidence for one says nothing about the others.

Correspondence

Do two representations agree?

model ↔ code

drifter check

This is drifter's exact job. If the code has an open endpoint, a model derived from that code records it as open, and the check stays green.

Conformance

Does it meet an independent obligation?

code → authored rule

pytestruffpip-auditownership.json

Tests, lint rules and the CVE database are written independently of the change being judged, so the work can actually fail them.

Acceptance

Will the receiving environment take it?

result → gate

branch protectionreview

Whether main admits the PR. Today that's anyone who pushes.

"The independence that matters … runs between the source of the obligation and the realization being evaluated against it."§3.2.1. This is why an ownership.json read at the PR head isn't independent: the change can rewrite its own obligation.

§3.3Four roles: constraint, sensor, validator, gate

There are two pairs. Constraint and sensor act on the work: one prevents, the other observes. Validator and gate act on evidence: one judges, the other enforces. "Prefer a constraint where the unwanted state can be excluded cheaply and reliably."

"Wiring a validator's verdict into a gate is a commitment. Making an uncertain validator blocking converts its false positives into rejected work." That's why pytest can block from day one but drifter check stays advisory.

Re-derive at admission

"The thing asking to pass does not get to define what counts as having passed." CI re-runs the tests itself rather than trusting an agent's "all tests pass", and ownership should be read at the PR base, not the head.

Enforcement is conditional

A hard control doesn't mean "the system is correct." It means that, within a stated scope, acceptance no longer depends on the agent voluntarily satisfying the obligation. A behavioral model with 0 states is green over an empty observation surface.

§3.3.7Under- and overconstraint

A = realizations that satisfy the obligations. P = realizations the controls permit. Ideally they match. Each mismatch is a different failure.

Underconstraint · P∖A

Bad work gets through, which threatens correctness. Here: no gate at all, so P is "everything". A non-owner can grant themselves ownership in the same push.

Overconstraint · A∖P

Good work gets refused, which costs engineering freedom. Here, if drifter blocked: renaming a parameter or moving a file counts as drift, because the grain is close to a symbol table.

§3.4Governance conversion: turn failures into structure

"The repair fixes this instance. Conversion changes the environment." When something fails, diagnose what was missing before adding another gate. The fix can land in five places.

1 · representationImprove the model

The fact wasn't represented.

2 · obligationState the boundary

"Free" variation wasn't actually acceptable.

e.g. a forbidden-imports table
3 · evidenceAdd a sensor

The state wasn't observable.

4 · evaluationStrengthen the validator

No repeatable judgment existed.

e.g. INVALID_MODELS, BOTS
5 · enforcementAdd a constraint or gate

The verdict controlled nothing.

e.g. branch protection

The book's cautionary story: correct judgment without enforcement

A merge bot auto-resolved conflicts by picking one side.
Sensor ✓ detected conflicts on critical files.
Validator ✓ judged the resolution unsafe and logged a warning.
Gate ✗ it proceeded anyway, and content was lost.

The fix wasn't a louder warning. They removed the unsafe capability. Rule: a temporary warning-only check needs "an owner and resolution condition." For this repo, that means drifter check advisory, owned by a named person, until fewer than 10 false alerts per 100 red checks.

"Non-enforcement is sometimes the engineered result." Not every check should block. The page lists where each should land. Today every check is at best "evaluated only", because there's no gate.

Engineering capital

Durable structure that lowers the future cost of change: a model, a constraint, a validator, a gate, a runbook. It's the opposite of technical debt: "capital lets future work inherit today's judgment."

…and it depreciates

A validator can encode an assumption the architecture has outgrown. A sensor gets noisy, and a gate can cost more than the failure it prevents. "A governed environment with more mechanisms is not necessarily richer." Maintain, reconcile or retire.

§3.6The five moves, applied

  1. Enforcement makes an obligation more than a request. AGENTS.md asks; branch protection requires.
  2. Place each check where it becomes decidable. ruff can run at the action boundary. pytest, pip-audit and drifter need the whole PR. "Does it serve?" needs the runtime.
  3. Correspondence is not correctness. Drifter keeps models and code agreeing, and tests plus authored rules say what's right. Write at least one architecture rule.
  4. Convert recurring judgment into structure. Every past bug that became a test is capital, but it only pays off when CI runs it.
  5. Govern the governance machinery. Catalogue the controls, watch for collisions, and give every advisory check an owner and an exit.
